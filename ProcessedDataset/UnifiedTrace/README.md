# Unified Trace conversion

The default conversion reads the three filtered 1k samples in `../../OriginalDataset-filter-1k/`. A separate entry point can convert the full filtered sources in `../../OriginalDataset-filter/`. Source filtering and sampling profiles live under `OriginalDataset-filter/`; this directory contains Unified Trace conversion and validation.

The standard converter reads only `OriginalDataset-filter-1k/`, whose samples
come from `OriginalDataset-filter/`. To convert all rows in the filtered full
sources, run `python scripts/convert_filtered_full.py --output-dir <new-output-directory>`.
It streams WildChat shards and reads SWE main transcripts in filtered Session-log
order. `--limit-per-source N` is available for a smoke test and marks its output
as a limited test. Neither conversion entry point performs Session sampling or
removes whole source records. Dataset-level eligibility is decided by the
scripts in `OriginalDataset-filter/`.

The scripts write `traces.parquet`, `events.parquet`, `schema_inspection.json`, and `conversion_report.json`. Re-running with the same sample files yields the same trace IDs and event order. Parquet compression is Zstandard. `traces.parquet` has seven columns: `trace_id`, `source`, `source_id`, `query_type`, `language`, `model`, and `user_turn_count`. `events.parquet` has six: `trace_id`, `event_id`, `role`, `event_type`, `content`, and `visibility`. Event counts are derived by grouping `events.parquet` by `trace_id`. Original event IDs, timestamps, and event metadata are used during conversion diagnostics but are not written to either table.

## Mapping

WildChat rows map one-to-one to traces. Each filtered WildChat source removes empty-content Conversations and retains the first eligible row of every `conversation_hash` within that source; overlap between the two sources is not removed. Trace IDs use a fixed seven-digit suffix, such as `WildChat_1M_0000001` and `WildChat_4_8M_0000001`; this covers the 4.8M source while preserving lexical order. The suffix is the one-based row position in each sampled `train.parquet`. The sample manifest stores selected filtered row indices and the corresponding original global row indices; the filtered source also has `kept_original_indices.parquet`. Each conversation message maps to one event in list order. The original `conversation_hash` is retained as `source_id`. IP hashes, browser headers, country, state, safety/moderation annotations, and message-level turn identifiers remain only in the source sample files. Post hoc moderation annotations must not be treated as information available at an earlier cut point.

SWE-chat is sampled by unique `session_id` from `OriginalDataset-filter/SWE-Chat-filter`, using seed 42 by default. That filtered source removes Sessions with no extractable main-agent interaction content, Sessions lacking a main transcript, uninterpretable main transcript formats, and Sessions with an identified tool result that has no matching tool call ID in the same main transcript. The sampler validates that every retained Session has one readable, exclusively mapped main transcript; it does not silently exclude more Sessions. The full-source profiler under `OriginalDataset-filter/scripts/` identifies 14 retained structural format families. The sample script balances the format families as far as their populations permit, then cycles through observed variants within each family. Variants combine the source agent label, JSON layout, file-size tertile, and nine structural feature bits. The agent label helps coverage but never chooses the parser. This 1k sample is for conversion testing and is intentionally not proportional to the full dataset's CLI frequencies. The selected Session IDs in `sample_manifest.json` are joined to both sampled metadata tables by `session_id`. Each Session maps to one trace. SWE trace IDs have the `SWE_Chat_0000001` form; the seven-digit suffix is the one-based position in the sample manifest. `source_id` remains the original Session ID. The SWE adapter chooses a parser solely from the raw file's structural format; the Session `agent` label has no role in event extraction. JSON documents stored with a `.jsonl` suffix are parsed as documents. Unknown records within a recognized format and genuinely malformed JSONL lines remain represented by `metadata_event` with their serialized/raw content.

Records are processed in source order and assigned sequential `event_id` values starting at zero within each trace. One identified human message produces one `user_message` event. Multiple user content blocks stay together as one JSON-serialized array in their original block order; a single plain text block stays a plain string. Assistant and tool records may expand to several events. Within one object that stores separate fields without an explicit sequence, the fixed order is the message body (user or assistant, as identified by the source envelope), thinking, all tool calls, then all tool results. A real user's body is never divided into thinking or tool events. Gemini follows the fixed order within a `gemini` record; Copilot results occur in later `tool.execution_complete` records and stay at those source positions. Explicit content lists retain their listed order. This fixed field order cannot prove within-record chronology. `event_id` is a new index and is never taken from a raw event ID, timestamp, or Session ID. Top-level JSON document headers are not events. Tool names and call IDs are no longer guaranteed to be recoverable from `events.parquet`; use the sampled raw transcript for those details. Explicit Claude `isMeta` records, Factory `llm_only` records, and recognized source-generated auxiliary content inside user-role records are omitted. Protocol tool feedback is still converted to `tool_result`. Text retained as a user body is never parsed again as a tool, thinking, or system event merely because it contains event-looking tags or JSON.

For SWE-chat, `user_turn_count` counts distinct delivered source prompts. Usually this is the number of source records that yield a human `user_message`; multiple content blocks from one record count once. xAI uses `promptIndex` to group chunks of the same prompt, and exact repeated chunks are not counted again. Validation reparses every sampled SWE transcript and compares all stored event IDs, roles, types, content, and visibility against the source conversion in original order.

## Full SWE format inventory

`OriginalDataset-filter/scripts/audit_swe_formats.py` inspects the first records of every main transcript under the original `transcripts/` and `transcripts1/` directories and writes `OriginalDataset-filter/full_swe_format_audit.json`. For JSON documents it inspects the first message envelope; for pretty-printed documents it uses the first top-level key. This distinguishes Gemini's `sessionId` envelope from OpenCode's `info` envelope even when a later Gemini message has type `info`. The inventory identifies 15 structural format families across 17,819 files; 14 families are eligible for sampling. The two reconstructed Zed files, one empty `{}` file, and one `_swe_chat_unparsed` wrapper are excluded. The inventory reads headers; it does not assert that every later record in every full-dataset file has the same structure.

The stratified 1k sample includes all 14 eligible format families, including simple `type`/`message`, `role`/`content`, and xAI `session/update` records. Simple messages preserve the source string; Codex `response_item.item` uses the same tool mapping as `payload`; Oh My Pi uses Pi messages and treats custom tool execution starts as system events; xAI updates distinguish message chunks, tool calls, completion results, and lifecycle events. Reconstructed Zed prompts and the two noninterpretable files are excluded before sampling and rejected by the converter.

The SWE implementation keeps one parser class per CLI format in `scripts/swe_cli_parsers.py`. `scripts/swe_common.py` holds transcript reading, JSON serialization, and content-block expansion. `scripts/swe_chat_adapter.py` selects a parser from the raw record envelope or inspected file format, assigns sequential event IDs, and counts user turns. `scripts/wildchat_adapter.py` keeps row and message conversion in `WildChatAdapter`. Sampled and full filtered conversion share the six- and seven-column Parquet definitions in `scripts/unified_schema.py`.

Dataset-level filtering and CLI record inclusion rules live under
`OriginalDataset-filter/scripts/`. The SWE adapter imports those rules and
performs only event extraction and schema mapping. In particular, the filter
removes Sessions without main-agent interaction before sampling; the adapter
identifies embedded sidechain records while reading otherwise valid main-agent
logs. An `agent-*` name alone does not establish subagent status.

Format review on the current sample: Codex `response_item` records are preferred for assistant text; otherwise an `event_msg.agent_message` becomes an assistant message. Codex `event_msg.agent_reasoning` is internal thinking. Standalone runtime wrapper blocks such as `<environment_context>`, `<turn_aborted>`, `<skill>`, `<subagent_notification>`, and a complete `# AGENTS.md instructions for ... </INSTRUCTIONS>` block are omitted from user-role messages; unrelated content blocks in the same message are kept. Claude user-role text consisting solely of a closed `<system_instruction>` or `<system-reminder>` envelope is omitted. Droid user-role pure `<system-reminder>` blocks are omitted individually. OpenCode user-role `compaction`, `agent`, and pure internal `<system-reminder>` parts are omitted. If an otherwise retained user text block contains an envelope followed by other text, the complete block is kept as a user message. Kimi uses `message.origin.kind=user` for human input, omitting `injection`, `task`, and duplicate `turn.prompt` records. Copilot omits `user.message` records with a non-human `data.source`; Pi omits user-role messages with agent attribution. Copilot `assistant.message.toolRequests` represents the tool call, while `tool.execution_start` is a separate system execution event. Grok `Stop.last_assistant_message` supplies assistant text when present. Gemini tool results serialize both the structured `result` and its `resultDisplay` when present. These rules follow transcript structure, not the model name in session metadata.

Pi `toolCall.arguments` becomes tool-call content; OpenCode user `file` parts remain structured user-message content. An xAI `user_message_chunk` that repeats the same payload within the same `promptIndex` group is dropped without creating an event. When `promptIndex` is absent, a shared source `agentTimestampMs` or `promptId` can identify the group; without such a marker, identical text is preserved because independent user submissions cannot be ruled out. Distinct chunks with the same prompt index count as one source prompt. Claude user-role records can contain separate protocol `tool_result` blocks and human text blocks. A tool-result block emitted by the CLI is distinct from text in which a human merely mentions or pastes a tool result. The explicit protocol result stays a tool result; the human text stays a user message, except the observed `Tool loaded.` notice alongside `tool_reference` feedback, which is an environment event. Both blocks retain their original order.

The `visibility` labels are coarse categories. `public` means ordinary user or assistant text; `environment` means tool or injected system material; `internal` means thinking or bookkeeping. They do not prove what any participant saw.

For SWE-chat, trace-level `model` uses the unique model identifier attached to main-agent responses or turns in the raw transcript. If several distinct main-agent models appear, `model` is null because one scalar value would be misleading. When the main log has no model identifier, a non-generic `sessions.parquet.model` value is used; `auto`, `auto-smart`, and `default` are treated as unspecified. Sidechain records never supply this field. WildChat `model` comes directly from its sampled Parquet row.

The converter reads only the selected main transcripts under `transcripts/` and `transcripts1/` plus Session and Session-log metadata. It does not read compact transcripts, subagent transcript files, or subagent conversation tables. Explicit `isSidechain` records, Claude `agent_progress`, Grok subagent hooks, xAI subagent lifecycle updates, and Pi `custom_message` records with `subagent-` or `subagent_` types embedded in main logs are ignored by the local `scripts/swe_record_policy.py`. A main agent's own tool call and returned tool result remain main-agent events even when the tool delegates work. Session outcome scores, summaries, and document summary fields are not copied into chronological events. UnifiedTrace imports only code in its own `scripts/` directory; its format detector, CLI parser, and record policy currently match the corresponding local copies under `OriginalDataset-filter/scripts/`.

`scripts/audit_full_swe_adapter.py` parses every available main transcript file in the filtered full SWE source and writes `full_swe_adapter_audit.json`; it verifies every filtered main file and never writes a full converted dataset. `scripts/audit_swe_expansion.py` checks source-order expansion of retained explicit content blocks in the 1k sample. `scripts/audit_swe_structured_outputs.py` checks original structured tool inputs and outputs against parsed events. `scripts/audit_user_body_boundaries.py` checks that retained user-body blocks do not become assistant/tool events, source-marked auxiliary records emit no events, and grouped Gemini/Copilot fields use the fixed order.

## Interpretation limits

- Event timestamps and source event IDs are intentionally omitted from the streamlined table. The converter still counts missing source values before removing those columns; see `conversion_report.json`. The original sampled transcripts remain unchanged.
- The agent's raw `user` role does not always prove human authorship. Explicit source markers are preferred. Some Claude/OpenCode/Codex/Droid auxiliary envelopes are recognized from their text because their source records lack an independent author marker. A human who pastes the same envelope verbatim cannot be distinguished perfectly; inspect the original transcript before treating such a case as settled.
- No trace-level partial flag is written. Source anomalies such as invalid JSONL, unmatched tool-call IDs, and a result preceding its call remain in `conversion_report.json`. A tool-result ID without a matching call ID excludes its entire Session during filtering, before this converter runs. A complete byte-for-byte copy of the available source file does not imply that the agent task succeeded. JSONL is split only at LF, so Unicode line separators inside message content do not create false parsing failures. Genuinely malformed JSONL lines are retained verbatim as metadata events.
- Empty-content SWE Sessions are excluded by `OriginalDataset-filter/scripts/filter_empty_swe_sessions.py` before sampling. The sampled 1,000 Sessions must each yield at least one nonblank user, assistant, thinking, or tool event; validation rejects any zero-content trace.
- A Copilot assistant message may contain tool requests before separate execution events. Both source records are represented, but their native type and call ID require inspection of the original transcript.
- Some Codex `event_msg.user_message` records repeat `response_item` user messages, while review-mode records can be generated UI prompts. The `event_msg` copies remain `metadata_event`. Recognized runtime wrapper blocks inside `response_item` are omitted; the source does not always independently prove whether an identically formatted block was generated or pasted by a human.
- A CLI log may contain a tool request without a corresponding explicit result; no results are invented. In particular, Gemini tool-call records with only an ID, arguments, and `status: success` do not contain a result payload, so they produce a tool call but no tool result. Grok Stop failure messages remain system events rather than assistant replies.
- Tool calls without a matching result can reflect cancellation, truncation, or format differences. The validator reports these without inventing results.
- `query_type` is a nullable string and is null for all 3,000 traces. None of the sampled source schemas contains the benchmark's seven-category Query Type labels. No source annotation is mapped to this field, and neither `Other / Unknown` nor any third-party WildChat Topic label is inserted. Query Type classification is a separate downstream stage using one rubric across all three datasets; missing labels here are expected and pass validation.

See `schema_inspection.json` for observed source structures and `conversion_report.json` for conversion counts, data-quality checks, and overlap analysis.
